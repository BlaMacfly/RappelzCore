# Real MariaDB crash/restart during two-client reward processing

Verified **2026-10-31** with **51/51 independent checks**, two ordinary native Windows x64 clients, and a real force-kill of the isolated MariaDB process. The same worldserver and authserver remain running. A committed positive-currency/level-up reward survives; a second real award interrupted before COMMIT is fully rolled back and is never announced. This extends [worldserver-only currency/level restart coverage](MONEY_LEVEL_RESTART_VALIDATION.md).

## Production defect and fix

A regression first reproduced a cleanup defect: when a periodic or lobby save failed, `Session::save` left its in-game player attached. Normal disconnect cleanup could fail again, retain the world's sender to the socket writer, and leave a ghost player/connection. The new closed-pool regression fails against the previous code with `failed save retained a phantom session`.

Failed full-character saves now detach the world/player state before returning the error. Disconnect cleanup also detaches after any leave failure. It does not retry a stale snapshot after an uncertain SQL outcome. Session/world socket senders are dropped and the writer closes **before** best-effort auth-database cleanup; that cleanup has a two-second timeout. The existing reward-specific failure guard remains. No schema, reward arithmetic, combat formula, inventory erasure or wire packet is added.

During the real outage the owner is already blocked in a reward write and disconnects promptly when MariaDB is killed. The witness sends a real ReturnLobby while SQL is unavailable; its pool acquisition reaches the existing roughly 30-second limit, then the corrected failure path detaches it and closes the connection. Rendering continues while that request waits. The worldserver is not restarted to clear ghost state. New login and normal save paths subsequently recover through their existing SQL pools.

## Actual sequence

1. Both clients fight normally; the witness assists for three hits and cancels. A real settings-row lock holds the first reward write for **798 ms**. Normal SQL and the native client retain the old progress until COMMIT; dirty reads show the in-progress candidate. Release the lock and independently verify the complete private award: owner becomes level **3**, remaining EXP **4**, JP **10**, money **1009** (**+9**), HP/MP **140/70**. No later manual save is issued.
2. Wait for the same monster's ordinary respawn in the still-running world. Start a second real cooperative fight; witness assists for two hits and cancels, leaving the owner the killing blow. A new owned settings-row lock holds the second reward. Across **806 ms**, normal SQL still sees the first committed profiles, while dirty reads see EXP **9** and money **1020** (another potential +11) with the **old JP 10** because settings REPLACE has not completed. Native owner remains at EXP 4/JP 10/money 1009/level 3. The intended second JP total 13 is never announced.
3. Kill owned MariaDB PID **3516** with exit **1**, **13 ms** after the verified locked-window observation. World PID **31072** remains alive throughout. The owner's active transaction fails; no second reward is published. Witness attempts its ordinary lobby save while the database stays down. Both production connections must close and both client workers join before restart is allowed.
4. Reopen the same database directory as PID **29836**, **31.326 seconds** after kill. The recovery log explicitly reports crash recovery, **43 pages** to recover, **one transaction / one row operation** to undo, and `Rolled back recovered transaction 2541`. Normal SQL profiles now equal the complete first committed profiles exactly, and the pending transaction ID is absent. There is no mixed EXP/JP/currency record, post-crash import or repair UPDATE.
5. Only after independent SQL verification may both clients reauthenticate against the unchanged auth/world processes. Owner handles change **2→3→5** across three entries, witness **1→4→6**. Second login loads the first reward's exact level/vitals/currency; witness retains its own checkpoint, level and wallet. Observe at least 3.2 seconds without old combat/routes/targets/rewards, capture identical ground, then coordinate a new ordinary witness movement.
6. Both return normally to the lobby, the resulting SQL saves are read, then a third entry must load the same award and exact vitals. Finish with another normal lobby exit. World PID 31072 eventually shuts down normally only after validation is complete; recovered MariaDB is handed off for preservation checks and then stopped normally.

Both observers receive identical **10-hit and 9-hit** sequences for the two kills, then **zero hits** in both later entries. Owner EXP packets are 799/7 → 4/10 → 4/10 → 4/10; gold packets are **1000→1009→1009→1009**. Neither 9/13 nor money 1020 is published. Witness remains EXP/JP 0/0 and money **2000**. Both see one level-3 update; only owner emits one Lua PLAYER_LEVEL_UP. Each client produces three real Lua login/entry/logout events; PLAYER_MONEY counts are 4/3. All **six world workers join** and both native processes exit 0.

Post-session SQL confirms both new character/account sessions offline, same-realm sentinel 0 and other-realm sentinel **2** before explicitly restoring the new sentinels. Account/character online flags can remain stale during failed writes; this case does not run world-start cleanup during recovery. Ordinary reauthentication and final saves restore the fixture session state.

Both recovered ground PNGs match their checkpoint captures exactly; the recovered RappelzDebug UI was inspected showing level 3, money 1009, JP 10 and 140/70. The fixture camera remains obstructed by scenery as documented previously; this is not a scene-placement/geometry acceptance test. Terrain payload remains bounded at **60 MiB/client**, with the existing 128 MiB CPU cap and four uploads/frame. Twelve real Windows counter samples cover the two settled holds; pair Total Committed peaks there are **5518.33/5542.83 MiB**, not an optimization claim.

## Guarantee and remaining scope

A previously committed/announced reward survives this database **process** crash with durable InnoDB settings. An uncommitted second award rolls back completely, is not announced and is not automatically retried. A killing-blow packet is not a durable reward receipt. This does not implement an exactly-once death/loot journal, replay of unannounced rewards, whole-host power-loss testing, storage failure, distributed writers, or original formula fidelity.

Repeat on a fresh isolated clone. Stop its bootstrap database normally, then let the guarded controller own the new process on the retained directory. Use the existing currency fixture, `database_restart: true` in controller/native plans, matching database executable/config/SHA in the controller plan and the existing probe plan. Run the controller and existing reward probe with two real clients, preserving initial checkpoint/counters, first committed reward, second locked window, both-dropped-before-database-restart, independently recovered-profile-before-login, post-observation and saved-profile-before-third-entry gates. Use `compare_database_restart_clients.py`, original/copied-content checks and both branch builds before publication. Never kill a numeric PID loaded from a file or restart/reimport the original service to perform this test.
