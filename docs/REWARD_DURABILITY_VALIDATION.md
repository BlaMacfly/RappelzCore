# Rewards committed before notification and retained after process crash

Verified **2026-10-31** with two ordinary native Windows x64 clients, real combat, an actual database row-lock wait, worldserver process kill and restart on persistent isolated cloned data. The successful final attempt passes **49/49 checks**. A real old-server control fails because it announces XP/JP while the save cannot commit.

Subsequent native coverage: [positive currency and level-up after crash](MONEY_LEVEL_RESTART_VALIDATION.md) validates +14 rupees, level 2→3, EXP rollover and 140/70 saved vitals with 57 checks. The zero-gold/level-1 evidence below remains historical.

## Production change

`Session::handle_world_event(Reward)` now builds a candidate from the live character snapshot, applies EXP/level, JP and currency to that candidate, and awaits the existing transactional `characters::save`. Only after successful COMMIT does it replace the session character, send private EXP/JP/gold packets and publish level/stat/reward notices. A level-up candidate includes the same full HP/MP that the existing world level update applies. Normal saves therefore cannot later overwrite the reward with an older in-memory total. No world mutex is held across database I/O; the normal session event loop serializes rewards and saves.

A failed SQL write never publishes a reward. Its outcome can be uncertain if a connection is lost around COMMIT, so the session detaches its world entity and ends without a normal stale-character disconnect save. This preserves any transaction that may already have committed. Existing login recovery reads the durable state. Other characters, inventory rows and unrelated extras are preserved. No automatic retry or success claim is made for an uncertain commit.

Reward arithmetic saturates within the existing storage types: EXP/money at u32 maximum, JP at i64 maximum; negative award inputs do not subtract progress. Existing provisional EXP/stat formulas remain. Candidate tests cover level 2/799 EXP plus 5 EXP becoming level 3/4 EXP, JP increment, positive gold, full level-up vitals, original-candidate isolation, unknown extras and saturation. A closed-pool test covers failure, absence of gain packets and a subsequent disconnect that cannot issue a stale save.

The original schema is unchanged. XP/money/level/vitals and Rappelz settings (including JP) still use one existing character UPDATE/settings REPLACE transaction. There is no new packet, reward journal or migration.

## Limits and repeat procedure

The guarantee is COMMIT before reward notification and retention after **worldserver process failure** while MariaDB remains alive. A crash before the reward transaction commits can still lose an unannounced kill reward. Database/whole-host power loss, original death/loot journaling, idempotent retry across ambiguous commits, distributed writers and broader latency/load remain unverified. The native monster awards zero gold and does not level these fixtures; positive-gold and level-up candidate behavior have Rust coverage but are not claimed as new native positive-currency/level-up measurements.

Use a fresh isolated clone and new fixtures beyond measured existing-ID bounds. Reuse the restart plan/config/path/SHA guards, choose controller `scenario: "reward-durable"`, and set `durable_rewards: true` in both native role plans. Run the controller, `reward_commit_probe.py <server-plan.json> <probe-plan.json>` and two native clients together. The probe plan uses `mysql_executable`, isolated `fixtures`, `existing_character_max` and `existing_account_max`, as in the earlier rollback workflow. Keep checkpoint/capture gates, require `reward-crash-verified` before down-state/restart permission, verify scoped online cleanup before login, and verify saved SQL profiles before third entry. Do not issue a second console save to make this test pass. Run the existing gameplay comparer, preservation checks and both branch builds/tests before publication. Historical `save-rollback` reward expectations describe the previous server version; use its retained copied binary when reproducing that earlier case.
