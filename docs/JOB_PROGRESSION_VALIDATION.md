## Lossless companion profile

`rz-extractor progression --client <original> --out <Data-or-dbc-root>` reads the three unambiguous archive entries directly. It adds only `Progression/{BasicStat,Exp,SummonExp}.dbc`, preflights all existing destinations, preserves conflicting files and is idempotent for identical files. Full client conversion also attempts this optional profile; `rz-extractor dbc` transfers an existing valid companion to the server.

The dedicated shared `ProgressionBook` uses signed 64-bit values throughout. BasicStat converts to eight 32-bit cells; Exp uses a level plus five low/high u32 pairs (**11 fields, 44-byte records**); SummonExp uses a level plus three pairs (**7 fields, 28-byte records**). The legacy generic 32-bit DBC converter is unchanged. Readers validate schema, exact total size, bounded counts, canonical levels, duplicate IDs, signs and relevant monotonicity; missing or malformed companions disable progression rather than inventing data. Growth/evolve/JP columns may legitimately return to zero.

An independent Python comparison checks every original field against both installed profiles, including all high words. Original EXP exceeds u32 at level 147 and exact double precision at level 213; row 300 is **272233208401492000**. Native reports retain that value as a decimal string. Generated DBC hashes are BasicStat `5f5b7db596a5a2450bd619fde5a48579fbe7e98a4d5b3d45c5a4028d56b57c64`, Exp `5569e410800cea391697babe9745368e2fe7247beeeaf5035ccb73f6df564ba5`, SummonExp `83cd550078896fa971d603b71e1d0afe0ecf896232dc05c3b521409ad5fbb51c`.

**Historical EXP semantics are retained.** The pinned reference [adds cumulative EXP](https://github.com/NGemity/RZEmulator/blob/38ceb2c6065fabf6ff4ba71d52f955f362c6c839/Chihiro/src/Entities/Unit/Unit.cpp#L1416) and [looks up level-1 thresholds](https://github.com/NGemity/RZEmulator/blob/38ceb2c6065fabf6ff4ba71d52f955f362c6c839/Chihiro/src/Globals/ObjectMgr.cpp#L1425). That is not proof of the supplied customized SFrame's complete progression rules, and it differs from the current remaining-EXP/u32 character model. No XP migration, reset or replacement formula is performed. Summon EXP is loaded as data; this does not implement pets/summons.

## Current-job purchase and UI

The supported slice uses **current JLV row × job depth 0–3** to select the exact JP column. This follows the pinned [cost lookup](https://github.com/NGemity/RZEmulator/blob/38ceb2c6065fabf6ff4ba71d52f955f362c6c839/Chihiro/src/Globals/ObjectMgr.cpp#L1365) and [job-level action](https://github.com/NGemity/RZEmulator/blob/38ceb2c6065fabf6ff4ba71d52f955f362c6c839/Chihiro/src/Network/GameNetwork/WorldSession.cpp#L871). The initial local policy supports purchases **JLV 1..49 → at most 50**, rejects cost zero as a limit and leaves higher/unknown jobs intact. The longer depth-3 column does not silently authorize higher job levels. This reference is not asserted to match an official Epic/patch.

Server checks the exact current owner/GUID/account, life, absence of active casting, supported data and sufficient JP. The full character snapshot debits JP and changes `jlv` in the existing single SQL transaction. Only after COMMIT does session state change, private EXP/JP and `job_level` property publish, visible observers receive the existing LEVEL_UPDATE and the learning catalog refresh. SQL failure detaches/closes without retrying stale state. No heal, character-level increase, stat bonus or inherited-job calculation is guessed.

An associated defect was fixed: a session whose world player was removed/replaced could still snapshot and save its old character. Snapshot/save/learn/reward paths now reject lost world ownership without writing that old state or removing the replacement. This covers the reproduced stale-session path, not a distributed/session-fencing implementation for every concurrent-login race.

Native K UI adds **Augmenter le métier**, the authoritative cost, insufficient-JP disabling and clearly labeled **Base métier** attributes. The private `SC_JOB_PROGRESS` **62012** extension is sent only after native skill opt-in; it is not claimed to be an original opcode. Existing recovered CS 410/LEVEL_UPDATE/EXP_UPDATE/property/result packets remain in use. Lua adds read-only `GetJobLevel()`, exact decimal `GetJobPointsExact()` and `RAPPELZ_JOB_LEVEL_CHANGED`; no Lua purchase action is exposed. The existing numeric JP API/event retains Lua 5.1 double limitations.
