# Successful reward COMMIT with its confirmation lost

Verified **2026-10-31** with **47/47 independent checks** and two ordinary native Windows x64 clients. A real reward transaction commits successfully in MariaDB, but its actual SQL OK is withheld and discarded before reaching the worldserver. The owner disconnects without a premature reward announcement; reconnecting reads the complete saved gain, without a stale cleanup overwrite or duplication. The witness returns normally to the lobby on its healthy connection. This extends [database process crash/recovery](DATABASE_RESTART_VALIDATION.md), which covered an interrupted, uncommitted award.

## Isolated fault and observed outcome

Original services on **3310/4615/4514**, their PIDs and data remain unchanged. A fresh retained clone owns MariaDB **3331**, auth **24615** and world **24514**. Only the cloned character SQL pool passes through a loopback relay on **3332**; auth/world database queries and the independent SQL observer go directly to 3331. The database stays in PID **7380**, created before world PID **1820** starts. No database, auth or world process is restarted during the scenario.

The new clone-only characters **34/35**, sentinel accounts **36/37** and additive spawn **1499** follow the existing currency fixture. Owner starts at level 2, EXP 799, JP 7, money 1000 and HP/MP 120/60; witness starts at level 1, EXP/JP 0/0, money 2000 and HP/MP 100/50. Existing monster 651 data is unchanged: HP 105, EXP 5, JP 3, gold 8–14. Original spawn 1498 and every copied pre-existing world INSERT remain exact. One pre-combat console save establishes moved checkpoints 9452/7235 and 9452/7255; no post-award manual save is used.

1. Both clients participate in real combat and receive the same **10-hit** sequence. The witness assists for three hits, then cancels; the owner delivers the single killing blow. A settings-row lock holds the real reward UPDATE before settings REPLACE. Independent SQL lock inspection identifies backend connection **156**, with a row-modified waiting transaction. Only that connection's next exact COM_QUERY COMMIT is armed.
2. Release the lock and forward the real COMMIT. The relay receives its actual **11-byte**, sequence-1 OK, with server status **2** (no open transaction). It retains that response for **773 ms**, then discards it and resets only that SQL connection. It neither fabricates a success response nor sends the held OK to the worldserver.
3. Across **569 ms** of independent committed reads and fresh native telemetry, SQL already contains level **3**, remaining EXP **4**, JP **10**, money **1013** (**+13**) and HP/MP **140/70**, while the client still has level **2**, EXP/JP **799/7** and money **1000**. Native telemetry remains within the existing 150-ms liveness lease. No level-up, EXP or currency gain is announced before the error.
4. The owner receives one real transport failure and its client world drops/joins. The existing backend uncertainty guard detaches the player without saving the old in-memory progress over the committed row. A direct read after disconnect still matches the complete committed owner profile. The witness receives **zero transport errors**, moves back to its checkpoint and performs a normal lobby save on the same connection. Its own wallet/progress/settings stay unchanged; real damage and later ordinary regeneration are allowed.
5. Wait for the monster's ordinary respawn in the same world, then enter again: owner performs real authentication, while witness enters from its existing character screen. Both load their exact saved profiles and observe each other's correct level and maximum vitals through ENTER. A quiet interval rejects stale movement, targets, combat and reward replay. A subsequent coordinated witness move, normal lobby saves and a third entry verify durability again.

Owner gold packets are **1000 → 1013 → 1013**; EXP/JP are **799/7 → 4/10 → 4/10**, each later packet being the new world's initial state. There are **no level-update packets or PLAYER_LEVEL_UP events** in this case: the original success announcement was withheld by the failed COMMIT result, and reentry initializes the already-saved level. Witness remains at EXP/JP 0/0, money **2000** and level 1. Both clients emit three real Lua PLAYER_LOGIN, PLAYER_ENTERING_WORLD, PLAYER_LOGOUT and PLAYER_MONEY events. Later worlds receive zero hit packets. All **six terrain workers join** and both native clients exit 0. The controller and independent probe also exit 0; the copied world shuts down normally after the final lobby exits.

Recovered RappelzDebug was visually inspected at level 3, money 1013, JP 10 and 140/70. Ground captures match their initial checkpoint images byte-for-byte for both clients. The fixture camera remains obstructed by scenery; this is not a geometry/scene-placement acceptance test. Terrain texture payload peaks at **60 MiB/client**, retaining the 128 MiB CPU limit and four uploads/frame. Twelve Windows counter samples cover settled initial/recovered holds; pair Total Committed peaks are **5382.08/5404.58 MiB**. These are observations, not a memory optimization claim.

## Tools and bounds

`mysql_commit_proxy.py` accepts only the explicit isolated ambiguous/currency plan, separate loopback ports and character-only proxy routing. MySQL v10 handshake parsing extracts the real backend connection ID and clears only CLIENT_SSL/CLIENT_COMPRESS for this local test hop, so framing is observable. Production TLS settings are unchanged. Other handshake bytes, queries and replies pass unchanged. SQL credentials/query bodies are never logged; retained OK metadata includes length, status, timestamp and SHA-256. Limits are **1 MiB/frame**, **16 concurrent accept/handshake tasks**, **256 events** and a **25-second** held-response deadline. The comparer rejects protocol errors, overflow, wrong connection/sequence, forwarded OK, premature native gains, stale writes, peer failure or an unexpected database/world restart.

`commit_confirmation_probe.py` locks only new fixture settings, observes SQL directly, correlates the selected transaction and releases real reentry after verification. `commit_confirmation_server.py` owns the copied world and relay; it never kills a PID from an input file. `compare_commit_confirmation_clients.py` reuses packet epochs, damage chains and worker audit readers. The optional native driver's `ambiguous_commit: true` mode adds the expected owner error and ordinary witness lobby path under its existing currency/durable profile. No production server code, schema, packet, reward formula or automatic replay is added in this cycle.

## Guarantee and continuation

For this real successful backend COMMIT with a lost response, the existing failure guard prevents a stale cleanup overwrite. The owner discovers the complete saved reward on reentry, with no automatic duplicate award or private leak. An unannounced killing blow is still not a durable receipt. General exactly-once death/loot journaling, replay of uncommitted/unannounced rewards, whole-host power/storage failure and distributed writers remain separate work.
